# Pack: photography-family

Client-only category starter: a family, motherhood & newborn photographer's site at `web/app/src/View/PhotographyFamily/`. The photography category's light-and-airy reading — the register the Pixieset-paying family photographer actually shops for — and the category's first pack with REAL session booking: the studio's session types x weekly availability project into concrete bookable times on the managed booking domain, alongside the platform proofing service the flagship photography pack carries.

## What ships

- A seven-page site on the landing kernel's romantic-stationery register (`heirloom` preset — warm ivory, Fraunces serif with an italic accent, champagne hairlines, botanical green, generous air; `docs/landing.md` "The photography-grade set"), deliberately apart from photography's dark `tourbook` field journal, the music pack's `marquee` stage-night, and the wedding pack's `lanternlight`:
    - **Home** — full-bleed crossfade hero (one frame from each body of work), a justified selected-work gallery with lightbox, a short introduction beside the portrait, collection covers, one featured kind word at pull-quote scale, and a booking CTA
    - **Work** (`/work`) — album collections as large cover tiles; each opens via `?album=<slug>` on the same route (the BlogBot `?post=` pattern — adding an album is a content edit, never a route edit) into a justified, lightboxed gallery with its own sequencing
    - **Galleries** (`/galleries`) — the client-facing proofing story, in the nav on every page (the owner mandate: photography templates must allude to proofing on the site itself, or nobody discovers what the template does after a shoot). Walks the after-the-session flow as a timeline — a private gallery arrives by email behind an access code, the family taps the frames they love, Maeve hand-finishes the picks — then a sample section steps visitors into the Ashford demo room (`/proof?album=ashford-family`, access code printed in the copy) to try the real gate and selection tray. The sample section's copy derives its slug and code from `demoProofingAlbums` (pinned by test, never drift); after publish the photographer re-aims or removes that one documented section while the rest of the page stays true for real clients
    - **Investment** (`/investment`) — the page converting photographers look at first: three flat-priced session offerings on the pricing section (`period: ""` suppresses the SaaS "/mo" reading; equal monthly/yearly suppresses the billing toggle), how a session unfolds as a timeline, and an FAQ accordion of the questions families actually ask
    - **About** (`/about`) — portrait beside the narrative, kind words from the families
    - **Book** (`/book`) — **online session booking**: the SessionBookingWidget projects the studio's weekly windows x session types (mini 30 min, full session 90, newborn planning call 45) into capacity-1 bookable times, picked as session → date → time and held with a name and email. Live availability from the `/__booking` door on a deploy; workspace simulation with the same provider-overlap rule, so a taken evening never double-books in either world. The platform's DB-owned schedule source lands behind the same door with no template change
    - **Inquire** (`/inquire`) — a detail form with session-type/date fields plus direct contact channels; submissions deliver through the platform's managed forms pipeline (`formKey: "inquiry"`) — the photographer gets an email and a dashboard entry with zero setup, and the email address shows as copyable text (never a `mailto:` link)
    - **Proofing** (`/proof?album=<slug>`) — unlisted client galleries in selection mode. On a published site the page asks for the access code, then loads the room from the platform door `GET /__proofing/room?slug=&code=` (same-origin, like `/__forms/submit`). The code is checked **server-side** and never ships in the site bundle. The family picks frames (persisted locally so they can return), adds their name, email, and an optional note, and sends the selection to `POST /__proofing/select` as `{ slug, code, visitorName, visitorEmail, note, picks: [imageId…] }`. The room itself stays out of the nav — the photographer shares the link and code after a session — but the **Galleries** page tells every visitor the room exists and links the sample
- **Public pages render from `content.ts`** — photographer, albums, investment, about, booking offering, inquiry copy: one typed file. Live proofing rooms do not: they come from the platform. `demoProofingAlbums` in that file is demo-only (see below)
- **The booking offering is contract data**: `codeAppointments` in `content.ts` is the code fallback for the business-content contract's `appointments` domain (the catalog's `content` seed mirrors it entry for entry, pinned by the content tests), so the Manage session calendar opens on exactly the offering the site shows, and the platform projects exactly the capacity-1 slots the sandbox simulation offers
- Demo portfolio: a coherent fictional family photographer (Maeve Callahan, Santa Barbara) with three sequenced albums — golden-hour families on the coast, in-home newborn mornings, childhood at the shore — processed through `npm run image -- responsive` into `web/app/public/photography-family/`; every image ships intrinsic dimensions and a WebP `srcSet`, so pages load layout-shift-free and phones never download desktop files
- When the pack is active it owns `/`, `/work`, `/galleries`, `/investment`, `/about`, `/book`, and `/inquire`; otherwise the same pages preview under `/photography-family`, `/photography-family/work`, ...

Set [`../active.json`](../active.json) to `{ "key": "photography-family" }` to make this pack the home surface.

## Register and special fields

Every field below belongs to a section _variant_, not to the register, so a remix to any other `style.preset` keeps it; the register only restyles it (docs/landing-content.md → "The registers" lists every preset and treatment). Text is click-to-edit and photographs Replace-able in the preview editor, and the content paths named are Content-panel slots in `catalog.json`'s `contentContract` (switches such as `home.layout` stay in code).

- **Register**: `heirloom` (no treatment flags); the documentary remix wears `snapshot` (`taped`, `tilt`, `grain`).
- **Hero** (`full-bleed-media`, the `crossfade` home): `slides` (`heroSlides`, each Replace-able as `slides[i]`), `badge` (`home.badge`); an optional `seal` (`home.note`, null here).
- **Hero** (`pinboard`, the documentary remix's home): `prints` (`heroSlides`, each Replace-able as `prints[i]`, with a `caption`), `badge` (`home.badge`), the handwritten `credit` (`home.scribble`) and the `seal` note (`home.note`).
- **Checklist** (pinboard home only): `feature-grid` `checklist` with its `cardTitle`.

## Agent recipe: make it yours

- Change the photographer: edit `photographer`, `home`, `albums`, `investment`, `about`, `book`, `galleries`, and `inquire` in `web/app/src/View/PhotographyFamily/content.ts`. The headings, kickers, and button labels around them (and the masthead's layout and tagline) are `landingCopy` in the same file.
- Change the home composition: `home.layout` is `crossfade` (this site: the slideshow hero and justified walls) or `pinboard` (the documentary remix's pile of taped prints and scrapbook walls, which also renders `home.day`, `home.expect`, `home.scribble`, and `home.note` when they're filled), or `builder` (the Ada Lin remix's window photograph over the session builder in `home.builder`: groups with `choose` `one` or `many`, lines with a printed `price`, a photograph, and `selected` for the package that opens ticked), or `specimens` (the Ashgrove remix's photograph over the prints in `home.prints`: each process with a one-line `note`, the `price` it starts from, and its own photograph). The proofing room's chrome follows `proofing.voice` (`quiet` or `register`).
- Swap in real photographs: run each original through `npm run image -- responsive <file> --out-dir web/app/public/photography-family --alt "..."` and paste the emitted media entry into the album's `images`. Never commit raw camera files into media slots. Keep the art direction: soft natural light, unposed, warm — the light-and-airy register is the product.
- Sequencing is the craft: `justified` rows preserve your image order exactly (unlike masonry) — order each album the way the session unfolded: open strong, vary rhythm, close strong.
- Add an album: append to `albums` in `content.ts` with a unique `slug`; the work page's cover grid, the `?album=` detail view, and the home teaser all follow.
- Reprice the sessions: edit `investment.offerings` — flat dollar amounts, an includes list each, and exactly one `highlighted: true` (the page reads better with a spine).
- Change the booking offering: edit `codeAppointments` — session types carry the slot length they book (5–240 minutes); the weekly windows are numbers (`day` is the weekday index, 0 = Sunday; `start`/`end` are minutes since midnight). Slots pack back-to-back from each window's start; the workspace widget and a deploy project identical slots. Keep the catalog's `content.appointments` seed mirroring it — the content tests pin the mirror.
- Client galleries are a platform service, not a content-file edit. After publish, the photographer creates rooms in the Manage console (name, photos, share link + access code). Do not add live rooms to `content.ts`.
- `demoProofingAlbums` is **demo fixture data only**: baked template previews and the funnel's console preview have no site router, so `/proof` falls back to these rooms when the door is unreachable. Keep one well-populated room (the Ashfords, `/proof?album=ashford-family`, preview PIN `5417`) looking like a real client gallery — the funnel screenshots it AND the Galleries page's sample section walks visitors into it (`galleries.sample` derives the slug and code from the fixture; the content tests pin the linkage). Proofing albums never appear on `/work` or in the nav.
- Content tests guard the file: every image carries dimensions + alt text, album and demo-proofing slugs stay unique, every demo room carries a preview PIN, the appointments contract parses contract-clean and mirrors the catalog seed, and the booking copy stays free of platform naming.

## Preview vs published

The kernel's booking and forms clients already treat a missing reserved path as sandbox. Proofing mirrors that: `fetchProofingRoom` / `submitProofingSelection` (`web/core/src/Proofing/ProofingClient.ts`) call `/__proofing/room` and `/__proofing/select`. A JSON door answer (including `invalid_room_code`, `proofing_room_not_found`, `proofing_not_configured`, 429) is always shown. Only an unreachable path (network failure, HTML 404 from a static preview) falls back to `demoProofingAlbums`. A published site whose door returns 503 `proofing_not_configured` shows a calm "galleries aren't set up yet" state, never the demo rooms. Booking is the same discipline on `/__booking/appointments` and `/__booking/book` (`web/core/src/Booking/BookingClient.ts`): a real door's domain outcomes (slot taken, duplicate booking) are always relayed; only an unreachable door simulates against the page's own generated slots.

## Non-goals for this pack

- Deposits, payments, contracts, and reminders at booking time (booking-domain upgrades, not template features — holding a time takes a name and an email)
- Full-res delivery, downloads, watermarking, per-image comments, and real client accounts (the access code is the gate; those remain platform proofing v2)
- Auth / accounts, e-commerce print or album sales
- Per-site backends — published sites stay static CDN assets and plug into the platform doors
