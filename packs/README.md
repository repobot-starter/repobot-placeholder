# Template packs

Vertical overlays for `repobot-base`. Each pack lives under `packs/<key>/` with catalog metadata (`catalog.json`) and an agent recipe (`PACK.md`). Packs are the top tier of the repo's reuse model — they own only their vertical's content and compose the kernels below them (see `docs/kernels.md` for the kernel/chassis/util/pack rubric).

## catalog.json contract

- `key` — pack key; matches the folder and `active.json`.
- `templateKey` — the platform's template id: the GitHub template repo name and the project picker key.
- `base` — required: the base-template family this pack belongs to, one of `landing | app | store | game | content`. The platform's workspace groups projects around ~4 configurable bases (landing page, web app, store, game) and presents complete vertical starters separately; `base` names the family a pack starts from — the physical clustering that already exists (all `View/Site` packs share the full-stack app chassis → `app`; everything under `View/Games/` → `game`; `launch` → `landing`; `shop` → `store`; content-first singletons like blog/folio/link/menu/quiz/flash and the AI chat/voice starters → `content`). **The vocabulary is append-only**: the platform's `TemplateRegistry` mirrors it in lockstep, so never rename or remove a value — only add one (and add it on the platform side in the same motion). Enforced by `scripts/verify-pack-catalogs.mjs` (check-all) and `compose-pack.test.mjs`; compose emits it into `repobot.deploy.json` so the platform can place a project without re-reading the pack catalog. Judgment calls on record: `blank` is `app` (the placeholder's simple landing page is incidental chrome — "no template" means "build from scratch", and the general-purpose configurable base is the app one; no `blank`/`none` value was minted for a single pack), `auth` and `invoice` are `app` (users experience them as applications — an accounts scaffold and a form-to-PDF tool), `sugar` and `trade` are `landing` (conversion-first marketing pages: host-a-machine and quote CTAs) while `menu` stays `content` (informational site for existing customers — hours, menu, directions — not a conversion page).
- `isFeature` — optional, `true` on **feature packs**: one-page feature apps (PDF generator, Stripe checkout, AI document interpreter, data entry, QuickBooks sync) that work standing alone as a project AND can be added into an existing project. The platform's add-a-feature flow unions the pack's `capabilities` into the project's `repobot.deploy.json` and exposes its preview route as a page, without switching the active pack — which works because every composed project already carries every pack's views at their preview routes. Must be exactly `true` when present (omission, not `false`, is the "not a feature" signal), mirroring `isBase`; the platform's `TemplateRegistry` carries the same flag. Feature packs are exempt from the compose-ready approval bar (their product is the tool, not a composable marketing site — same reasoning as games). Compose emits it into `repobot.deploy.json`.
- `isBase` — optional, `true` only on the canonical configurable base of a family: `launch` (landing), `saas` (app), `shop` (store). Every other pack omits it (omission, not `false`, is the "starter project" signal). The game family deliberately has no `isBase` pack: the workspace's game base tile is a picker across the game packs, so no single game is the canonical starting point.
- `category` — optional: the marketing-site category this pack starts (`photography`, `services`, and coming: `weddings-events`, ...). Category starters are the successor naming scheme to the bot-persona templates: the first starter in a category takes the bare category key as its pack key; later alternates get suffixed keys and share the `category` value so pickers group them. Append-only vocabulary, mirrored by the platform like `base`.
- `clientOnly` — `true` means deploys ship the built web app statically and skip functions, migrations, and database provisioning until the manifest changes.
- `capabilities` — provisioned-infrastructure badges (`AUTH`, `DATABASE`, `EMAIL`, `BACKEND`, `PAYMENTS`, `AI`, `DOCUMENTS`, `STORAGE`, `JOBS`) shown in the picker and read by the platform to decide what to provision and inject (`PAYMENTS` adds the deploy-time `STRIPE_SECRET_KEY` from the account's connected Stripe integration; `AI` adds the deploy-time AI gateway credentials — keyless, billed to the account's platform credits — or the account's own `OPENAI_API_KEY` when an OpenAI integration is connected; `DOCUMENTS` adds the deploy-time `DOCUMENTS_RENDER_URL` + `DOCUMENTS_TOKEN` for the platform's PDF render service; `STORAGE` adds the deploy-time `STORAGE_MODE=gcs` + `STORAGE_BUCKET`/`STORAGE_PREFIX` for the environment's object storage; `JOBS` provisions one Cloud Scheduler job per environment and adds the deploy-time `JOBS_MODE=scheduler` + `JOBS_TOKEN` so the jobs registry ticks on a real schedule).
- `authMethods` — optional, packs with `AUTH` only: the sign-in methods this template ships (see `docs/auth.md`), defaulting to `["email-code"]`. Compose emits it into `repobot.deploy.json` (driving the platform's auth provisioning and the deploy-time `VITE_AUTH_METHODS`) and stamps `AUTH_METHODS` into the native config files.
- `contentContract` — optional: the pack's content slots as data, for design-space composers (agents and platform tooling that generate variants of the pack rather than hand-editing it). `module` names the pack's typed content file; `slots` maps slot paths to `{ kind, min?, item? }` where `kind` is one of `text | text[] | number | media | media[] | collection` (collections nest an `item` slot map; `number` is a bare numeric value — a price, a count — that a composer must bind as a number, never prose). The contract is authored alongside the content module — the module satisfies it, the pack's content tests guard it, and it never drifts ahead of what the module actually renders. Declaring one (together with `landing` seeds for every routed page) is what makes a pack **compose-ready**: `scripts/generate-design-manifest.mjs` computes the flag and publishes the pack's block in `docs/design-manifest.json`; `scripts/verify-pack-catalogs.mjs` validates the shape. `photography` is the reference implementation. New packs should ship one from day one; existing packs join only when promoted.

Packs that sell things declare the `PAYMENTS` capability and reuse the kernel payments domain (`paymentsService` checkout sessions, the Stripe webhook, the `purchases` ledger, and session-gated delivery) — never bespoke Stripe wiring. A pack owns only its server-side product catalog and a thin create mutation, mirroring the shop exemplar; prices never come from the client: see `docs/payments.md`. In the sandbox checkout is simulated for free (`PAYMENTS_MODE=local`); deploys get real Stripe Checkout via the account's connected Stripe integration.

Packs that need user accounts declare the `AUTH` capability and reuse the kernel auth component (`AuthCard`/`AuthScreen` behind `ProtectedRoutes` and the `/login` route; native `SignInView` twins) — never a bespoke login form. Enabled methods and branding are configuration, not new UI: see `docs/auth.md`.

Packs (and upgrades) that want an assistant declare the `AI` capability and reuse the kernel chat surface (`AiChatThread` over `useAiChat` on web; the `AiChatStore`/`AiChatComponent` twins on iOS) — never bespoke streaming plumbing. Voice packs likewise compose the kernel voice broker (`AiVoiceService` on the backend; the `AiVoiceStore`/`AiVoiceComponent` twins on iOS), never their own Realtime wiring. Web hold-to-talk (the `agent` pack) composes `ai__request__voice` over ElevenLabs STT/TTS around the same chat brain. Customization is the system prompt, the voice instructions, and domain tools in `AiChatTools.ts`: see `docs/ai.md`. In the sandbox both chat and voice are simulated for free (`AI_MODE=local` / `ELEVENLABS_MODE=local`); deploys get the real models automatically — the platform's keyless AI gateway (billed to platform credits) or the account's own OpenAI and ElevenLabs integrations when they exist. Users never need to bring an API key.

Packs that generate PDFs declare the `DOCUMENTS` capability and reuse the documents kernel — templates as repo files under `firebase/functions/documents/templates/<key>/`, generation through `documents__request__api` — never bespoke HTML-to-PDF plumbing. A new document type is a new template directory, not new code: see `docs/documents.md`. In the sandbox rendering uses the machine's own Chromium for free (`DOCUMENTS_MODE=local`); deploys use the platform's render service.

Packs (and upgrades) that need recurring work (cleanup, digests, rollups) declare the `JOBS` capability and register jobs in the jobs kernel's registry (`src/Jobs/JobsRegistry.ts`: name + cron expression + handler) — never hand-rolled timers or bespoke scheduler wiring: see `docs/jobs.md`. In the sandbox an in-process ticker runs due jobs for free (`JOBS_MODE=local`); deploys get one platform-provisioned Cloud Scheduler job ticking the environment every 5 minutes.

Packs that store user files (avatars, product images, attachments) declare the `STORAGE` capability and reuse the storage kernel — `createUpload`/`finalizeUpload`/`fileUrl`/`deleteUpload` plus `putUploadBytes` from `@base/core` — never bespoke bucket wiring or filesystem writes: see `docs/storage.md`. In the sandbox files live on local disk for free (`STORAGE_MODE=local`); deploys get a provisioned Cloud Storage bucket with V4 signed URLs.

Packs that grow multi-destination navigation reuse the kernel application shell (`AppShell` on web; the `NavigationShellView` twins on iOS/Android) — never a bespoke sidebar. Navigation is data against the shell nav schema (sections, items, badges, hotkeys, drill-down levels), so changing a product's IA is config edits mirrored across platforms: see `docs/shell.md`. The shell needs no capability — it is pure kernel chrome.

## Derived templates (remixes)

A derived template is a distinct entry in the platform's picker built from an existing pack rather than a new view tree: a thin `catalog.json` declaring `remixOf` (the base pack key), its own `key`/`templateKey`/`title`/`description`, a `contentSeed` (a content module that is a structural twin of the base pack's `content.ts`, copied over it at compose/switch time), and a `theme` brand overlay merged over the base's. Everything structural — `homeViewDir`, capabilities, landing seeds, content contract — is inherited from the base; `scripts/verify-pack-catalogs.mjs` rejects a remix that redeclares any of it. The base pack's landing modules keep their copy trade-neutral and pull the few trade-owned strings from the content module's `landingCopy` export, so a seed swap retrades the whole site. Seeds live beside the base content module (e.g. `web/app/src/View/Services/landscapeRemix.content.ts`) and a parity test per base pack (`tests/View/<Pack>/remixSeeds.test.ts`) pins each seed to the base module's export surface so CI catches contract drift. The six `services-*` trades above are the reference implementations.

### Wearing a remix: the composer contract

Every path that puts a derived template on a tree — `scripts/compose-pack.sh` staging a published template, the dev/studio switch (`scripts/lib/pack-switch.mjs` `switchPack`), and the **platform's agent-free template flip** — must apply the SAME four artifacts, all derived from `resolveCatalog(remix)` (the base catalog wearing the remix's identity, theme, landing register, and seed):

1. **`packs/active.json` = the BASE pack key** (`resolved.activeKey`), never the remix key — the kernel's routers (`homePageByPack`), the native `ActivePack` constants, and every document stamp only know real packs.
2. **Document overlays** (`applyPackOverlays`): the resolved `theme` merged over `repobot.theme.json`, the resolved `landing` over `repobot.landing.json`, the resolved `content` domains over `repobot.content.json` — each stamped `pack: <base key>`.
3. **The content seed copy**: the resolved catalog's `contentSeed` file copied byte-for-byte over the base pack's `contentContract.module` (e.g. `electricRemix.content.ts` → `View/ServicesEmergency/content.ts`). This step carries ALL of a remix's trade content — business identity, copy, service names, `landingCopy` headings. It is not optional and is not covered by step 2: the trade lives in the content MODULE, not in the documents, so a flip that stamps the documents but skips the seed copy ships the base pack's trade (an "Electrician" site reading as the base plumber) under the remix's brand.
4. **Platform identity from the remix** (`repobot.deploy.json` `templateKey`/`packKey`), where the composer emits one.

The safest implementation is to reuse the kernel's own: `resolveCatalog` + `applyPackOverlays` + the seed copy are exported by `scripts/lib/pack-switch.mjs` (dependency-free Node, present in every published tree), and `switchPack` performs the whole sequence including the pristine-restore bookkeeping a flip needs. Kernel gates pin the contract: `scripts/compose-pack.test.mjs` asserts a composed remix tree carries the seed bytes, the base `active.json`, and the remix deploy identity; `scripts/verify-pack-integrity.mjs` fails a remix whose base pack or seed module is missing, and an `active.json` naming a remix key.

## Pack palettes and the theme contract

Packs own their art direction, but the customer's `repobot.theme.json` always
wins. A pack's style file declares its palette as constants that read the
pack-overlay custom properties, with the pack's own art palette as the
fallback:

```ts
const accent = "var(--pack-accent, #d95d43)" // the pack's own art palette
const accentSoft = "var(--pack-accent-soft, #fbe9e4)"
const sans = "var(--pack-font, Sora, system-ui, sans-serif)"
```

The full set is `--pack-accent`, `--pack-accent-hover`, `--pack-accent-text`,
`--pack-accent-dark`, `--pack-accent-soft`, and `--pack-font`
(`packBrandVarNames` in the design system's `themeConfig.ts`). The properties
are declared only when the project actually customizes the theme
(`tokens.css.ts` bakes them; `themeHotUpdate.ts` re-declares them on live
edits), so fresh templates look exactly as designed while "make it my brand
color" flows into every pack — and, because the value is read at paint time
rather than baked into the compiled CSS, a live theme edit re-inks the pack
in the workspace preview with no rebuild. Never hardcode an accent directly
in a new pack, and never bake `packBrand?.accent ?? …` into a style file —
route it through the custom properties.

## Composing a template repo

`scripts/compose-pack.sh <pack-key> <output-dir>` stages the kernel with the pack applied: sets `active.json`, stamps the pack key into the native `ActivePack` constants (`ios/App/Config/ActivePack.swift`, `android/.../config/ActivePack.kt` — the iOS/Android home surfaces switch on it, mirroring the web `homePageByPack`), and emits a root `repobot.deploy.json` (capability manifest read by the deployer). A pack that ships its own `repobot.project.json` (project IA, `docs/project-ia.md`) gets it stamped to the root and scaffolded (`scripts/scaffold-ia.mjs`) so the template arrives with its marketing pages and dashboard destinations wired — the saas pack is the exemplar. The platform's publish pipeline runs this per pack and pushes each staged tree to its GitHub template repo.

Compose also stamps a generated **agent map** into the composed `AGENTS.md` (`scripts/generate-agent-map.mjs`): the marker-delimited `## Pack map` section deriving routes, sections, view files, and user-editable surfaces from the catalog and the pack tree, so a fresh template's first agent message works from a map instead of exploring the repo. It is never hand-written — `scripts/check-agent-maps.mjs` (check-all + CI) dry-runs the generator for every approved pack and standalone template and fails on maps that can't be produced or reference missing paths. A pack may add hand-authored guidance to the map through a designated `## Agent map notes` section in its `PACK.md`; the body merges verbatim, and any backticked repo path it cites is gated like the generated ones.

Agents upgrading a project (e.g. adding a backend to a game) should flip `clientOnly`/`capabilities` in `repobot.deploy.json`; the next deploy provisions the newly required infrastructure.
