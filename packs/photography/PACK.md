# Pack: photography

Client-only category starter: a gallery-first photography portfolio at `web/app/src/View/Photography/`. The first of the category-named marketing starters (no bot persona): the work leads, the chrome recedes.

## What ships

- A multi-page portfolio on the landing kernel's image-led register (`atelier` preset, `docs/landing.md` "The photography-grade set"):
    - **Home** — full-bleed crossfade hero (the photograph IS the page), a justified selected-work gallery with lightbox, a short introduction, collection covers, and an inquiry CTA
    - **Work** (`/work`) — album collections as large cover tiles; each album opens via `?album=<slug>` on the same route (the BlogBot `?post=` pattern — adding an album is a content edit, never a route edit) into a justified, lightboxed gallery with its own sequencing
    - **About** (`/about`) — portrait beside the narrative, kind words from clients
    - **Inquire** (`/inquire`) — a detail form with date/location fields plus direct contact channels; submissions deliver through the platform's managed forms pipeline (`formKey: "inquiry"`) — the photographer gets an email and a dashboard entry with zero setup, and the email address shows as copyable text (never a `mailto:` link)
    - **Book** (`/book`) — **online session booking** on the platform's managed booking domain (the care pack's exact door discipline, booking mode 2): session types as photograph-fronted cards with evocative descriptions (portrait session 90 min, engagement session 120 min, mini session 30 min), then a date and time from the photographer's actual weekly windows, then four fields — name, email, optional phone, first-session-or-returning. The pack-local `BookingWidget` consumes the same-origin booking doors through `BookingClient` (`@base/core`): live capacity-1 slots on a deploy, sandbox simulation with the same overlap rule in previews. No invented endpoint shapes — the widget only calls the kernel client the care pack calls
    - **Galleries** (`/galleries`) — the **client-facing proofing explainer**, in the nav: what happens after a shoot (a private link and access code arrive, the client sits with the sequenced frames, picks save as they go, one press sends the selection to the studio), told in the photographer's voice — which is also how a photographer evaluating the template sees the proofing service working as site content, not a console feature. A "Walk through a sample" card opens the demo Harlow room on `/proof` and shows its preview PIN, so a preview visitor can click through the real gate-and-choose flow; a closing banner hands off to `/book`
    - **Proofing** (`/proof?album=<slug>`) — unlisted client galleries in selection mode. On a published site the page asks for the access code, then loads the room from the platform door `GET /__proofing/room?slug=&code=` (same-origin, like `/__forms/submit`). The code is checked **server-side** and never ships in the site bundle. The client picks frames (persisted locally so they can return), adds their name, email, and an optional note, and sends the selection to `POST /__proofing/select` as `{ slug, code, visitorName, visitorEmail, note, picks: [imageId…] }`. Not linked from the site nav — the photographer shares the link and code after a shoot
- **Public pages render from `content.ts`** — photographer, albums, about, testimonials, inquiry copy, and the session offering: one typed file. `codeAppointments` is the business-content contract's `appointments` domain code fallback (the catalog's content seed mirrors it entry for entry), so the owner edits the session calendar in Manage and `/book` repaints. Live proofing rooms do not come from the file: they come from the platform. `demoProofingAlbums` in that file is demo-only (see below)
- Demo portfolio: a coherent fictional portrait/editorial photographer (Mara Voss) with three sequenced albums, processed through `npm run image -- responsive` into `web/app/public/photography/` — every image ships intrinsic dimensions and a WebP `srcSet`, so pages load layout-shift-free and phones never download desktop files
- When the pack is active it owns `/`, `/work`, `/galleries`, `/about`, `/book`, and `/inquire`; otherwise the same pages preview under `/photography`, `/photography/work`, ...

Set [`../active.json`](../active.json) to `{ "key": "photography" }` to make this pack the home surface.

## Agent recipe: make it yours

- Change the photographer: edit `photographer`, `home`, `albums`, `about`, and `inquire` in `web/app/src/View/Photography/content.ts`.
- Swap in real photographs: run each original through `npm run image -- responsive <file> --out-dir web/app/public/photography --alt "..."` and paste the emitted media entry into the album's `images`. Never commit raw camera files into media slots.
- Sequencing is the craft: `justified` rows preserve your image order exactly (unlike masonry) — order each album the way the photographer would sequence a portfolio.
- Add an album: append to `albums` in `content.ts` with a unique `slug`; the work page's cover grid, the `?album=` detail view, and the home teaser all follow.
- Change the session offering: edit `codeAppointments` in `content.ts` — session types carry the slot length they book (5–240 minutes), the photographer's weekly windows are numbers (`day` is the weekday index, 0 = Sunday; `start`/`end` minutes since midnight). Slots pack back-to-back from each window's start; the workspace widget and a deploy project identical slots. Keep the catalog's `content.appointments` seed a structural twin of the export (the booking tests pin it), and front each session type with a frame from the albums via `booking.sessionImages` — art from code, facts from the contract.
- Client galleries are a platform service, not a content-file edit. After publish, the photographer creates rooms in the Manage console (name, photos, share link + access code). Do not add live rooms to `content.ts`.
- `demoProofingAlbums` is **demo fixture data only**: baked template previews and the funnel's console preview have no site router, so `/proof` falls back to these rooms when the door is unreachable. Keep one well-populated room (Harlow, `/proof?album=harlow-session`, preview PIN `4271`) looking like a real client gallery — the funnel screenshots it, and the `/galleries` explainer's sample card links into it. Proofing albums never appear on `/work` or in the nav.
- The `/galleries` explainer is content, edit it like any page: `galleries` in `content.ts` carries the headline, the "How proofing works" steps, and the sample card. The sample card derives its shown access code from `demoProofingAlbums` so page and fixture can't drift — but the demo room only authorizes in previews (a published site's door checks real codes server-side). **After publish**, once the photographer has real rooms in Manage, repoint `galleries.sample` at a real sample room and its code, or rewrite the card as a plain "your link arrives by email" note.
- Content tests guard the file: every image carries dimensions + alt text, album and demo-proofing slugs stay unique, every demo room carries a preview PIN.

## Preview vs published

The kernel's booking and forms clients already treat a missing reserved path as sandbox. Proofing mirrors that: `fetchProofingRoom` / `submitProofingSelection` (`web/core/src/Proofing/ProofingClient.ts`) call `/__proofing/room` and `/__proofing/select`. A JSON door answer (including `invalid_room_code`, `proofing_room_not_found`, `proofing_not_configured`, 429) is always shown. Only an unreachable path (network failure, HTML 404 from a static preview) falls back to `demoProofingAlbums`. A published site whose door returns 503 `proofing_not_configured` shows a calm "galleries aren't set up yet" state, never the demo rooms.

Booking follows the same discipline with no demo fixtures at all: `/book` renders from `codeAppointments` (real content, not demo data), and `BookingClient` (`web/core/src/Booking/BookingClient.ts`) talks to the same-origin doors — `/__booking/appointments` for open slots, `POST /__booking/book` to hold one. A real door's domain outcomes (slot taken, duplicate booking) always relay to the visitor; only an unreachable door switches to the sandbox simulation, which projects the identical slots from the page's own contract and records bookings in localStorage — a genuinely taken slot never turns into a fake confirmation. The booking form carries a name, email, optional phone, and first-session-or-returning: nothing else, ever.

## Non-goals for this pack

- Full-res delivery, downloads, watermarking, payments, per-image comments, and real client accounts (access code is the gate; those remain platform proofing v2)
- Booking payments, deposits, reminders, or waitlists (booking-domain upgrades, not template features)
- Auth / accounts, e-commerce print sales
- Per-site backends — published sites stay static CDN assets and plug into the platform doors
