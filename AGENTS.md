### Building a site (landing pages + sections)

Landing-site asks are DECLARED, not hand-written into `web/app/src/View/*`.
On blank (or any pack), define pages in `repobot.project.json` and let
the runtime map them through kernel sections (`docs/project-ia.md`).

1. Add `marketing.pages[]` entries in `repobot.project.json`:
   `{ id, path, title, blueprint, description?, sections? }`.
2. For finished from-scratch pages, add `sections[]` entries with real
   copy/media: `{ id, type, variant?, headline?, body?, ctaLabel?,
   description?, image? }` (hero also supports `accent`, `badge`,
   `secondaryCtaLabel`). Use shipped `type`/`variant` names only.
3. Optional per-page layout edits live in `repobot.landing.json`
   (`pages.<pageId>.sections`: order + variants + copy/media overrides).
4. Verify with `npm run typecheck` — marketing pages are runtime-manifest
   surfaces, so no scaffold step is needed unless you also add dashboard
   destinations (`npm run scaffold:ia`).
5. Restyle via `repobot.theme.json`; manifests keep structure remixable
   because the section skeleton stays data, not bespoke JSX.

### Building an app (dashboard + sidebar shell)

App-shaped asks (dashboard, admin panel, CRM, tracker…) are DECLARED, not
hand-written. Declare destinations in `repobot.project.json`, run
`npm run scaffold:ia`, and the scaffolder wires the routes, the sidebar nav
(AppShell), and one page per destination — composed from themed kernel
components, so the result is restylable and remixable (docs:
`docs/project-ia.md`).

1. Add `dashboard.destinations[]` to `repobot.project.json`:
   `{ id, path, label, blueprint: overview|table|settings|custom, sections: [...] }`.
2. Each section is `{ id, type, title?, span? }` plus the content fields in
   the table below. Fill the content with REAL demo values (numbers, series,
   rows) so the page arrives finished, not placeholder. `span: "half"` puts
   consecutive sections side by side on one row.
3. Run `npm run scaffold:ia` (idempotent — re-runs never overwrite pages you
   have edited), then restyle via `repobot.theme.json`. Only hand-write a
   page body when no section type fits.
4. Verify with `npm run typecheck` — it confirms all the wiring. Generated
   pages and routes are already covered by the kernel's scaffold contract
   tests, and the marketing nav CTA auto-links the first destination, so the
   app is reachable from the site home with no hand-wired links. Do NOT run
   test suites for scaffolded pages or manifest/theme edits; suites are only
   worth their minutes when you changed shared kernel code (web/core,
   web/design-system).

## Theming and restyling

`repobot.theme.json` (repo root) is the project's theme contract: brand accent
colors, corner radius, density, font, and default light/dark mode. The design
system derives all its tokens from it, so **edit that file first** for any
"change the colors / make it feel more X" request — the whole app (and the
`/theme` style-guide page) re-skins from one edit. Escalate only when tokens
can't express the ask: component props/slots next, then eject the component —
copy it into `web/app/src/Theme/overrides/` and re-point its export in
`web/app/src/Theme/ui.ts` (the `@ui` registry every page imports from).
**Never edit `web/design-system/` itself** — it must stay pristine
(`scripts/verify-ds-pristine.mjs` enforces this) so platform design-system
updates can land without clobbering your work. Full recipes:
`docs/design-system.md`.

When a request has you inventing the look — a new page, section, or restyle
with no color direction from the user (no named colors, brand, mood, or
reference images) — default to an achromatic black/white theme: true
blacks/whites, grayscale surfaces, typography and spacing carrying the
design, at most one restrained accent when the design genuinely needs a
focal point. It is the safer design call. Any direction the user expresses
wins over this default, and a template's committed theme is never repainted
to satisfy it.

The project's logo is a contract too: `repobot.project.json`
`marketing.brand` names the committed marks under `web/app/public/brand/`,
and the kernel renders each on its own surfaces — `logo` (the full wordmark,
transparent background) replaces the text wordmark in every manifest-driven
marketing nav and the blog masthead; `logoMark` (the square mark alone)
covers icon-sized shell surfaces; `icon` is the app icon/favicon; `social`
(the 1200×630 share card, at `/brand/social.png`) becomes every page's
default `og:image`. Set `logo` and `social` together: without a social card
the SEO kernel falls back to the raw logo, which makes a poor share image.
`BrandMark` handles the sign-in surface and app shell. Keep that wiring;
when you build a custom nav or header by hand, use those exact files (never
a redrawn approximation) and keep the logo a link home. Stamping
`marketing.brand` never breaks kernel tests — they pin their own manifest
fixtures — so never remove brand entries to get a gate green.

Dashboard pages compose the kernel's widget components — `StatCard`,
`ChartCard`, `ActivityFeed`, `DataTable`, `SettingsGroups`, `FiltersToolbar`,
`ListDetailLayout`, toasts via `useToast` — instead of bespoke chrome. Charts
go through `ChartCard` only; **never import recharts directly** in app code
(it ships as a lazy chunk behind `ChartCard`, and raw usage breaks theming).

## Live workspace rules (Spaceboy workspace)

When this repo runs inside a Spaceboy workspace (streamed browser next to chat):

- The dev stack is **already running** with hot reload; edits appear in the
  user's preview automatically — including edits to the root manifests
  (`repobot.project.json`, `repobot.theme.json`, `packs/active.json`), which
  trigger a **full page reload**, not an HMR patch. A screenshot taken during
  that reload catches a loading spinner or the previous page — wait for the
  page to finish loading before screenshotting or concluding the content is
  stale; the manifest reload is reliable. Do not start/stop servers, run
  builds, or `npm install` unless explicitly asked.
- Never run `git` commands; the platform commits and pushes automatically
  after each request.
- Keep final summaries to one or two sentences.
- Write progress updates and summaries for the app's owner, not for an
  engineer — they are often non-technical (sometimes a kid building a game).
  Describe what is changing in their app in plain words ("Making the race
  track scroll", "Fixing the countdown"), never internal mechanics like
  tests, APIs, refactors, test hooks, or file names. If the user talks shop,
  you can match them.
- You can create images with your image generation tool (logos, icons,
  sprites, backgrounds, illustrations). When the user asks for an image —
  for the app or just for themselves — generate it and save it inside the
  project (e.g. `web/app/public/`) with a descriptive filename. The platform
  attaches images you create to your chat reply automatically, so don't
  apologize about not being able to show them.
- When the user attaches a screenshot or mockup of a page and asks you to
  match it, that image is a **design spec**, not an asset. Recreate the
  layout in HTML/CSS — never paste the attached file into the page as an
  `<img>` or background (`docs/landing.md`, Matching an uploaded screenshot).
- For image _processing_ (cropping a logo, removing a background, slicing
  artwork into cells, deriving favicons, sampling a design's exact hex
  palette with `palette`), use `npm run image -- <verb>` (run it bare for
  usage) instead of hand-writing pixel math — it computes crop geometry from
  the image content and refuses operations that would cut artwork badly.
- For _photographs and other large page imagery_ (galleries, full-bleed
  heroes, collection covers — anything a customer would upload at camera
  resolution), run the original through
  `npm run image -- responsive <file> --out-dir web/app/public/<dir>`:
  it emits sized WebP variants plus a paste-ready media entry with
  intrinsic `width`/`height` and a `srcSet`. Never commit a raw camera
  file into a media slot — without the dimensions the page loses its
  layout-shift-free loading, and phones download desktop-sized files
  (`docs/landing.md`, "The photography-grade set").
- For the _starter brand kit_ (no logo uploaded), one command does the whole
  job: `npm run brand:generate -- --name "Product Name"` emits the wordmark,
  square mark, app icon, and social card under `web/app/public/brand/`,
  replaces the default favicons, and stamps `marketing.brand` into
  `repobot.project.json`. Color comes from the committed theme accent (or
  `--color #RRGGBB`); pass `--svg mark.svg` to build the kit around your own
  mark instead of the generated lettermark. Never hand-write sharp scripts
  for this.
- To verify a page actually works — renders without crashes, console errors,
  or dead requests — run `npm run page:check -- /route` (multiple routes at
  once are fine). It drives the pod's own Chromium against the running dev
  stack, prints every page error and failed request, and drops a full-page
  screenshot under `.dev/page-check/`. When matching an attached design, add
  `--compare <spec image> --width <design viewport>` to get one labeled
  design-vs-build side-by-side PNG. Never hand-roll browser automation or
  install playwright/puppeteer for this; the browser and its driver are
  already on the machine.
- Platform work beyond this repo (sign-in methods, integrations, billing,
  scheduled platform tasks) is yours to propose, not refuse: when the
  `repobot` CLI is available (workspace sessions run logged in with a
  project-scoped key), run `repobot actions list` to discover what the
  platform can do right now (the catalog is the source of truth — never
  enumerate capabilities from memory or say a capability doesn't exist
  without checking), then `repobot actions propose` to put a confirmation
  card in this chat. Nothing executes until the user confirms the card;
  never redirect the user to another chat or dashboard for something the
  catalog covers.
- Some catalog actions do their own implementation work on confirm — the
  action's description says so. Sign-in methods (`SET_AUTH_METHODS`) are
  the canonical case: confirming that one card enables the AUTH capability
  and launches the platform's own wiring run. For those, propose the card
  and stop — do not also implement that capability in this repo yourself,
  even when the project lacks it entirely; session-side wiring duplicates
  the metered run the confirmation launches, on a different line than that
  run builds from. Frame your reply around the card as the step that does
  the job, never as a follow-up to work you already did.

## Invariants (never break these)

Shared code in this repo comes in four tiers — kernels (compose via config),
chassis (imitate the exemplar), utils (call), packs (edit content). Before
building anything that feels reusable, find its tier: `docs/kernels.md`.

- Resolvers never touch the database; they call services and dataloaders.
- Schema changes are SQL migrations first; Drizzle TS tables mirror the SQL, never drive it.
- Entity CRUD forms are backend-driven SchemaForms; never hand-build them in the web app.
- `gql` documents live only in `web/app/src/Graphql/Operations/Gql/`.
- Design system stays domain-agnostic; styling is vanilla-extract from theme tokens only.
- Secrets never enter git or `VITE_` variables; env vars go through `env.manifest.json`.
- Throw `RpcError`, not `Error`, in backend code.
- Authorization is two-layer: the Apollo gate authenticates every operation; per-resource role checks live in services, never resolvers (`docs/authorization.md`).
- Sign-in surfaces are never hand-built: any feature needing auth gates routes with `ProtectedRoutes` (web) and renders the kernel auth component — `AuthCard`/`AuthScreen` on web, the `SignInView` twins on iOS/Android. Methods are config (`VITE_AUTH_METHODS` / `AUTH_METHODS`), branding goes through the card's props and theme tokens (`docs/auth.md`). Mechanically enforced: `scripts/verify-auth-surface.mjs` (in `check:all`/`check:web`) fails password fields or interactive sign-in wiring outside the kernel auth components.
- AI surfaces are never hand-built either: features needing an assistant render the kernel chat component (`AiChatThread` on web, the `AiChatStore`/`AiChatComponent` twins on iOS) over the kernel's streaming client and Ai service. Voice follows the same rule: push-to-talk surfaces compose the kernel voice broker (`AiVoiceService` + the `AiVoiceStore`/`AiVoiceComponent` twins) — never bespoke Realtime wiring or client-side keys. Customization is the system prompt, the voice instructions, and domain tools in `AiChatTools.ts`, not new plumbing (`docs/ai.md`).
- App shells and sidebars are never hand-built either: multi-destination apps render the kernel shell (`AppShell` on web, the `NavigationShellView` twins on iOS/Android). Navigation is config against the shell nav schema (`shellNavSections.tsx` / the `KernelShellView` binders), mirrored across platforms — not bespoke chrome (`docs/shell.md`). Mechanically enforced: `scripts/verify-shell-containment.mjs` (in `check:all`/`check:web`) fails new hand-built `<nav>`/`<aside>` chrome and any rewiring of `AppLayout`/protected routes away from the kernel `AppShell`.
- Inactive packs are never deleted or gutted: every directory under `packs/` stays intact — catalog, home view, assets — whether or not it is the active pack. The pack library is the template's catalog, not dead code to clean up; switching what a project ships is an edit to `packs/active.json` (`packs/README.md`), never a deletion. Mechanically enforced: `scripts/verify-pack-integrity.mjs` (in `check:all`/`check:web`) fails any pack missing its directory, catalog, or home view.
- Landing LAYOUT is a data contract: the active landing page's skeleton — style preset, shell chrome variants, section order and variants — is read from `repobot.landing.json` (root), like the theme. Agents changing layout edit that document; section content interfaces stay in code (the page's config file); never inline the skeleton back into TS (`docs/landing.md`, "The layout document").
- Landing pages are never hand-built either: compose the kernel marketing sections through a `LandingConfig` (style preset + ordered sections) rendered by `LandingRenderer` — not bespoke heroes, pricing tables, or waitlist forms (`docs/landing.md`). **Exception — matching an attached screenshot:** the page must look like that screenshot, not like a kernel preset with the PNG pasted in. Recreate layout/type/color via theme tokens + `LandingConfig` first; eject a section via `@ui` when the kernel cannot express the chrome; never use the attached full-page file as hero/media. Then `npm run page:check` and compare.
- `web/app/src/View/Site/blueprints.ts` holds the _shared defaults_ every manifest-driven page starts from; its test pins the seed contract (the user's own words surfacing on their pages). Page-specific needs — CTA labels and anchors, section overrides, extra sections — belong in that page's inline `landing` config in `repobot.project.json` (`LandingConfig` already expresses `{ label, anchor }` CTAs and per-section overrides), never in a reshaped shared builder that changes what every other page gets.
- Document meta is never hand-set either: public pages declare title/description/OG by rendering the SEO kernel's `PageMeta` component (never `document.title` writes — lint enforces it), and `sitemap.xml`/`robots.txt` are generated from `repobot.project.json` at build — never hand-edited (`docs/seo.md`).
- The IA comes from `repobot.project.json` — extend it, don't bypass it. New marketing pages are manifest entries (rendered at runtime, no per-page route wiring); new dashboard destinations are manifest entries plus `npm run scaffold:ia`, which owns the `<ia:*>` managed blocks in Router/App/shellNavSections. Never edit inside those markers or hand-wire what the scaffolder wires (`docs/project-ia.md`). A finished custom page — the home page included — lands in the manifest page's inline `landing` config (or its sections), never in a TypeScript component that a route serves instead: rerouting `/` around the manifest leaves `repobot.project.json` describing a page nobody renders, and `verify-manifest-routes` fails the check.
- Checkout flows are never hand-built either: anything that sells keeps a server-side catalog in its own domain and composes the payments kernel (`paymentsService` sessions, the webhook, the `purchases` ledger, the `subscriptions` state table, session-gated delivery) — never bespoke Stripe wiring, client-side prices, or trust in a success redirect (`docs/payments.md`). A complete storefront already exists at `/shop` (`web/app/src/View/Shop/ShopPage.tsx`, catalog in `Services/Shop/ShopCatalog.ts`, copy in `shopContent.ts`): adapt it to what the project sells, then link it from the marketing nav or a CTA — never replace it with a static page about paying, which leaves the site with nothing buyable. Adapting comes **first**: a "Shop now" CTA that lands on the untouched starter demo (The Lighthouse Letters bookshop) sends users into content that has nothing to do with their project — worse than no CTA at all. `scripts/verify-shop-integration.mjs` (in `check:all`/`check:web`) fails any link to `/shop` while the storefront still carries the stock demo. Subscriptions follow the same rule with two extra invariants: subscription checkout is never anonymous (the mutations are authenticated, never in the public allowlist — recurring billing entitles an account), and entitlement checks always go through `paymentsService.hasActiveSubscription` (`Services/Saas` is the exemplar: plan catalog + `createSubscriptionCheckoutSession`, the `/subscribe` journey, the settings Billing card, the Billing Portal).
- File persistence is never hand-built either: anything that stores user files (avatars, images, attachments) composes the storage kernel — `createUpload`/`finalizeUpload`/`fileUrl`/`deleteUpload` over the `uploads` table, `putUploadBytes` from `@base/core` on the client — never bespoke bucket wiring, raw filesystem writes, or client-side storage credentials. Private files are never served without an owner check, and clients only ever see signed URLs (`docs/storage.md`).
- Recurring work is never hand-built either: anything that must happen on a schedule (cleanup, digests, rollups) registers a job in the jobs kernel's registry (`src/Jobs/JobsRegistry.ts`: name + cron expression + handler calling the owning domain's service) — never a hand-rolled `setInterval`/`setTimeout` or bespoke scheduler wiring. Handlers must be idempotent (the run ledger guarantees at-most-once per due time, not exactly-once across crashes), and a failing job never breaks the tick (`docs/jobs.md`).
- Pageview tracking is never hand-built either: visit counting goes through the analytics kernel — the `PageviewBeacon` mounted once in `App.tsx` over the `analytics__request__api` beacon, with rollups owned by the `analytics-rollup` job — never third-party analytics scripts, cookies, or client-side identifiers. Raw IPs and user agents are never stored; the visitor identity is a daily-salted hash computed server-side, and retention lives in `AnalyticsConfig.ts` (`docs/analytics.md`).
- Embeddings and retrieval are never hand-built either: anything that turns text into vectors goes through the embeddings client (`aiEmbeddingsService.embedTexts` — never raw embeddings API calls), and every similarity query goes through the retrieval helper (`aiRetrievalService.indexDocuments`/`searchTopK` over the `ai_embeddings` store — never hand-written vector SQL). Retrieval-backed answers are registered chat tools (`search_blog_posts` over `Services/BlogKnowledge/` is the exemplar), so they work in every `AI_MODE` — the workspace embeds with the deterministic local embedding, free and offline (`docs/ai.md`).
- Transactional email is never hand-built either: anything that emails someone adds a template to the mail kernel's registry and calls `mailService.sendTemplatedMail` (template key + variables over the shared `MailWrapper` transport) — never inline HTML, bespoke SMTP wiring, or sends that can fail the flow they ride on (`docs/mail.md`). Auth's code emails are the one grandfathered exception.
- PDF generation is never hand-built either: features that produce documents go through the documents kernel — a template directory under `firebase/functions/documents/templates/<key>/` (html + css + schema + sample) and the `documents__request__api` endpoint. A new document type is new template files, not new rendering plumbing (`docs/documents.md`).
- The brief is the promise ledger (`repobot.brief.json`): a nontrivial feature request becomes an ask (with acceptance assertions) before it becomes code, and a request that changes an earlier promise amends its existing ask — never re-mint ids, never erase. Compiled asks are realized only through the manifests, and `npm run brief:check` — not self-report — is the source of truth for whether an ask is done (`docs/brief-spec.md`). Small conversational edits the user watches land in the preview stay ledger-free.
- Tests are blackbox through GraphQL, using the Mocha context helpers.
- iOS follows Store → Component → View (`ios/App/SWIFT_IOS_STORE_COMPONENT_PATTERN.md`); iOS GraphQL operations live only in `ios/ApolloGraphql/Operations/`, and `AppGraphqlApi` is regenerated (`npm run graphql:ios:prebuild`), never hand-edited.
- Android follows the same Store → Component → View pattern (`android/app/KOTLIN_ANDROID_STORE_COMPONENT_PATTERN.md`); Android GraphQL operations live only in `android/app/src/main/graphql/`, and the schema is recomposed (`npm run graphql:android:prebuild`), never hand-edited.

## Mobile parity

If this project has the `IOS` capability (see `repobot.deploy.json`), user-facing
features should land on both web and iOS. After backend schema changes, run
`npm run graphql:ios:prebuild` to regenerate the Swift API. Full recipes:
`docs/ios-app.md`.

If this project has the `ANDROID` capability, the same applies to Android:
after backend schema changes, run `npm run graphql:android:prebuild` to
recompose the schema. Full recipes: `docs/android-app.md`.

You never decide which platform checks to run: `npm run check:all` reads
`repobot.deploy.json` and covers exactly what this project is built for —
including the iOS/Android builds where the machine has the toolchain, and
skipping them (explicitly, in its output) where it doesn't; the platform
builds native apps remotely.

Native device capabilities are rails, not suggestions — users install these
apps on real phones (TestFlight / APK), so features that need the hardware
should use it. In `ios/App/Capabilities/`: `Haptics` (fire at moments of
physical consequence — a scan landing, a save committing), `CameraPermission`
(check before showing any camera surface; route denial to
`openSystemSettings()`), `QrScannerCamera` + `ArCameraView` (QR scanning
with AR checkmarks anchored on the scanned codes), `PhotoCaptureCamera`
(square photo capture; upload through the storage kernel),
and `ObjectDetector` (generic CoreML detection — drop a `.mlpackage` into
the Xcode project and inject it). All of them compose the same
`ArCameraView` shell, so a camera surface is: create the camera component,
embed `ArCameraView(arFrameDelegate: camera)`, observe the component.
Push notifications are wired end to end (`PushComponent` + the Settings
"Notifications" card); notify through the backend push kernel rather than
inventing a channel.

## Quality gates

Run before declaring any task done:

```bash
npm run check:all   # everything this project is built for: codegen + lint + build + web tests (+ native builds where shipped) + prettier
npm test            # backend blackbox tests (needs: npm run dev:db:test && npm run migrate:test)
npm run test:web    # web component tests (vitest; no database needed)
```

**Cadence: once at the end, not after every edit.** The gates verify the
FINAL state of a task; running them per-edit multiplies minutes-long
builds across every intermediate state and verifies nothing the final
run won't. Sequence all the edits for a work unit first, then run the
gates one time. While iterating on a specific failure, run only the
failing test file — not `check:all`, not the full suite. Skip gates a
change cannot have touched (a web-only edit doesn't need `npm test`; a
copy edit doesn't need a rebuild). Deploys are never a verification
step — `deploy:dev`/`deploy:prod` run when deploying is the task, not to
check that code compiles.

Backend tests are not optional: the promotion gate runs the full backend
suite (`scripts/verify-backend-tests.mjs` — starts the embedded test
database, migrates, runs mocha) before any task merges, so a suite you never
executed will fail you at the finish line. Run it yourself first. New domain
logic — anything with business rules a user described (pricing, state
transitions, permissions, money) — ships WITH blackbox tests for those
rules, written against the GraphQL API like `test/Identity/` and
`test/Project/` (note: the Mocha context field is `this.apolloServer`).
Test files are compiled by `tsc` like all other backend code — narrow
`unknown`-typed GraphQL results (e.g. `executeOperation` data) instead of
leaving strict-mode errors that pass mocha but fail the build.

Template-shipped test files under `web/app/tests/` are pinned (hash manifest
at `web/app/tests/.pinned-tests.json`, verified by every check run): they
encode the kernel's promises — the seed contract, SEO defaults, brand wiring.
When one fails after your change, fix the code so the promise still holds;
weakening or deleting the test (or editing the manifest) is never the fix.
New behavior gets new test files, which are welcome and not pinned.
